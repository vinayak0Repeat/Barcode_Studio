# Barcode Studio — Shopify-Only Migration Plan (research & planning only, no code changed)

Written 2026-11-26. Task: can Barcode Studio run **only on Shopify** (Shopify-hosted App Home UI extension + Direct API access, no Railway, no database we host)? Answer below, with every platform claim sourced from live official documentation fetched on 2026-11-26, or marked **UNVERIFIED**.

**Method note:** Web access was intermittent during this research (the fetch tool repeatedly failed on some shopify.dev URLs and succeeded on others; all facts below were ultimately read live from shopify.dev on 2026-11-26). Local evidence comes from a full read of the repo (files cited as `path:line`). Where a claim could not be verified from current docs it is marked **UNVERIFIED** with the page to check. The locally installed Shopify AI Toolkit v1.5.2 skill files were also consulted (its App Home skill lists the App Bridge API surface, and its bundled `@shopify/app-bridge-types` 0.7.0 / `polaris-types` 1.0.7 type definitions were read directly).

---

## 0. Executive summary and verdict

**Verdict: Pure "Shopify-only" (App Home UI extension, no server of ours) is NOT POSSIBLE for Barcode Studio at feature parity.** Shopify's own docs restrict this model to "custom-distribution apps that don't need server-side logic," with a 64 KB bundle, a Preact/remote-DOM sandbox, and no webhooks or background jobs — and the app's single most important feature, printing millimetre-exact labels / saving PDFs, has no extension-side path: Shopify's only admin print surface (print-action extensions) serves the printable document **from your app's backend URL**. Five blockers (detail in §2 and §4): **(1) label printing/PDF, (2) the 64 KB bundle vs pdf-lib/bwip-js, (3) no webhooks/background jobs, (4) no realistic replacement for the SQL taken-set/counter/cache under concurrency at 5,700–50,000 variants, (5) custom-distribution-only, which kills the earlier App Store plan.** Recommendation: **stay on Railway (Option 4)**, drop the static-IP spend (the new IP allowlist rule does **not** apply to custom apps), fix the compliance P0s, and revisit Direct API access *inside the current iframe app* as a modernization, not a migration. Spikes in §5 settle the unknowns for ≈2–3 days of effort before any future decision.

### B. Converting the existing app in place

- Adding an App Home UI extension to an **existing** app is supported: "You can either add your extension to an existing app, or create a new extension-only app from scratch" — https://shopify.dev/docs/api/app-home-ui-extension/latest (`.md` alternate). Our app is already **custom distribution** (permanent choice; per the repo's own `docs/MULTI_STORE_ANALYSIS.md` citing shopify.dev distribution docs), which is the only distribution the extension model allows — so distribution itself is compatible.
- **Migration is one-way:** the comparison table says of the extension model "Reauthor as an iframe app if you outgrow the runtime. **The reverse isn't supported.**" — https://shopify.dev/docs/apps/build/app-home. I.e., you can leave the extension model later, but you cannot "convert" an iframe app into an extension app by flipping config — you rebuild the UI as Preact. Removing our `application_url`/redirect URLs from an installed app (what happens to existing sessions/scopes/webhooks) is **UNVERIFIED** — the docs describe extension-only apps from birth, not conversion; scope changes via managed install require merchant re-approval (same app-configuration page). This is Spike 7 territory, on a **copy** of the app only.
- Existing webhook subscriptions with HTTPS `uri`s would have nothing to hit if the server goes away; the TOML would have to drop them or point them at Pub/Sub/EventBridge (see I).

### C. Direct API access

- **Auth model:** "Call the GraphQL Admin API directly from your app's frontend with Direct API access, where **App Bridge authenticates each request**… An extension-only app has no backend, so it **never holds a token at all**" — https://shopify.dev/docs/apps/build/authentication-authorization. From the extension: "Any `fetch()` calls from your extension to the GraphQL Admin API are automatically authenticated by default. **You must declare all required access scopes in your app's TOML file.** Direct API can't be used to manage storefront access tokens." — https://shopify.dev/docs/api/app-home-ui-extension/latest. `shopify.query()` runs queries **and mutations**, "automatically authenticated with the current user's permissions", per-request API version — https://shopify.dev/docs/api/admin-extensions/latest/target-apis/core-apis/standard-api.
- **Access modes:** TOML keys `direct_api_mode = online|offline` (**defaults to `online`**) and `embedded_app_direct_api_access = true` (enables Direct API for the *iframe* model) — https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration. This confirms the preliminary notes: online by default, offline configurable — but an extension-only app still has no app-held token to use elsewhere; with online mode, **"a request can be refused even when your app holds the scope"** because online tokens are "narrowed to what the staff member who authorized it can do" — https://shopify.dev/docs/apps/build/authentication-authorization (staff permission gating confirmed).
- **API version:** pinned per app config / per `shopify.query` call (versions up to `2026-04` in the current admin-extensions reference; the Admin API itself is on `2026-07` stable / `2026-10` latest per https://shopify.dev/changelog).
- **Rate limits:** GraphQL Admin API uses calculated query cost; standard plan restore **100 points/s** (Advanced 200, Plus 1000, enterprise 2000); bucket keyed on **app + store**; single query ≤ 1,000 points; **input arrays ≤ 250 items**; bulk operations "don't have the max cost limits or rate limits that single queries have"; separate resource throttle: at 50,000 variants, ≤1,000 new variants/day via productCreate/productUpdate/productVariantCreate (not Plus) — https://shopify.dev/docs/api/usage/rate-limits. For extensions, documented plainly: "**GraphQL queries share rate limits with your app's overall Admin API usage**" — https://shopify.dev/docs/api/admin-extensions/latest/target-apis/core-apis/standard-api. So browser-side calls draw the same per-app+shop bucket our server uses today (no separate allowance).
- **Bulk operations from the extension:** `bulkOperationRunQuery`/`RunMutation` are ordinary mutations and exempt from per-query cost caps (rate-limits page above), but whether an extension-only app can *start* them and **download the JSONL from the browser** (storage URL CORS) is **UNVERIFIED** — Spike 4/3. Note the IP-allowlist interplay below.
- **IP allowlist (the Railway static-IP question):** the new rule is **public apps only**: "All public apps using bulk operations must configure an allowlist by **November 12, 2026**, and all other public apps … by **November 20, 2026**"; "What apps are unaffected: **Custom apps**; Apps created by merchants" — https://shopify.dev/changelog/posts/ip-allowlists-are-now-required-for-public-apps. So **today's custom-distribution Barcode Studio is exempt**, and the static-IP spend buys nothing for compliance today. Two caveats: (a) if the app ever goes public (the App Store plan), the allowlist becomes mandatory for server-side calls — static egress IPs would then matter; (b) the same post says of apps that "make Admin API calls from merchant infrastructure" (exactly what Direct API access is): "You should move as quickly as possible to an architecture that better limits exposure of Admin API tokens" and request a deadline extension — i.e., **browser-side Admin API calls are tolerated but explicitly not the security posture Shopify wants for public apps**. Whether the allowlist check applies to Direct API requests from merchant browsers is **UNVERIFIED** (Spike 3 notes it).

### E. Atomic counters and concurrency

- **`metafieldsSet` supports compare-and-set since API 2024-07:** "If `compareDigest` is set for any metafield, the mutation will only set that metafield if the **persisted metafield value matches the digest**" — https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldsSet. (Sending `compareDigest: null` gives safe create-if-absent semantics — third-party write-ups of the official docs; verify null-handling in Spike 2.)
- **What this gives us:** a CAS loop (read value+digest → set `next+n` with `compareDigest` → retry on mismatch) reproduces `allocateBlock`'s disjoint-block guarantee. **Guarantees kept:** no two sessions can draw the same block; numbers within a block are consecutive. **Guarantees NOT kept vs Postgres:** nothing else — no transaction spans "reserve block + read taken-set + write variants", so the *rest* of the protocol (taken-set freshness, all-or-nothing variant writes, compensation, burn) must be re-built around a live, possibly stale taken-set (see F). `releaseBlock`'s "only if tip" can be reproduced with the same CAS.
- **One-writer-per-shop lock:** buildable as a CAS'd metafield (lock row + lease timestamp) — but a crashed tab that set the lock and never released it needs a lease/timeout design; no DB-enforced transactionality. Possible-with-redesign.
- **Metaobjects:** no documented optimistic-concurrency/version field for entries — **UNVERIFIED**; treat metaobject writes as last-write-wins.

### F. Catalog access without a cache and without webhooks

- **Live reads:** `productVariants` supports cursor pagination; input arrays cap at 250 (rate-limits page). Search syntax exists for Admin API queries (filtering by fields) — https://shopify.dev/docs/api/usage/search-syntax (referenced from the resource-picker docs); exact filter strings for *empty barcode* / *duplicate barcode* are **UNVERIFIED** — Spike 3 must verify (e.g., `barcode:*`-style filters).
- **No server-side duplicate detection:** the Admin GraphQL API offers queries/filters, not GROUP BY/dedup aggregations — confirming duplicates must be **scanned and grouped client-side**. (No duplicate-aggregation query exists in the schema; treat "they cannot count duplicates" as confirmed by the API's shape.)
- **Scan cost (estimate from the documented cost model, not measured):** a page of 50 products × 10 variants costs roughly 500–600 requested points; the 1,000-point single-query cap forces ≈500 variants/query. ⇒ 5,700 variants ≈ 12 queries ≈ 6,600 points ≈ **~66 s at the 100 pts/s standard restore rate** (seconds on Plus); 50,000 variants ≈ 100 queries ≈ **~9–10 minutes on standard, ~1 minute on Plus**. Per Generate click. `metafieldsSet` adds `10 + Σ owners×weight` per call (Shop owner = weight 1). **Bulk operations** remove the cost cap (rate-limits page) and are the right tool for full scans — minutes per run, JSONL download, **UNVERIFIED from a browser tab** (Spike 3).
- **Webhook replacements:** no Shopify-hosted compute exists to refresh a shadow set on product change. Options: **(a) Next-Gen Events** — "declarative replacement for classic webhooks, now generally available across 18 topics" (https://shopify.dev/changelog, Oct 1 2026) with Product topic, custom GraphQL `query` in the delivery, and delivery to HTTPS / Google Pub/Sub / Amazon EventBridge (https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration) — but every delivery target is still *our* consumer; **(b) Shopify Flow** — Flow actions execute against an app-provided `runtime_url` (https://shopify.dev/changelog/release-notes/2026-07), i.e., our hosted endpoint again; **(c) refresh-on-open + `updated_at` incremental sync** — staleness between refreshes is unbounded (a variant created 5 minutes ago can collide with a newly drawn number if the taken-set is stale). **Verdict: duplicate prevention with Postgres-grade freshness is NOT POSSIBLE without either our own receiver (webhooks/Events) or accepting live-scan latency per write.**

### G. Long-running work without a server

- If the batch runs in the browser tab: **tab closed / session expired / network dropped = the driving loop dies** (in-flight `fetch` aborts). Progress can be persisted chunk-by-chunk into a metafield/metaobject (resume = re-read progress; rollback = compensation writes + burn), but nothing restarts it — a second staff member must resume manually, and mid-batch state is only as fresh as the last chunk checkpoint.
- **Shopify-hosted background work:** none fits. **Shopify Functions** domains are checkout/discount/cart-fulfillment domains (Discount, Cart/Checkout Validation, Cart Transform, Delivery/Pickup, Fulfillment Constraints, Order Routing, Payment Customization — AI Toolkit skill listing); none read/write the catalog or run on schedules, and Functions input queries truncate metafield values >10,000 bytes (https://shopify.dev/docs/apps/build/metafields/metafield-limits). **Flow** triggers/actions call our HTTP endpoints (2026-07 release notes above). **Bulk operations** *do* continue server-side once started and are pollable (`currentBulkOperation`), which is the one genuine "fire and check later" primitive — driving it from an extension-only app is UNVERIFIED (Spike 3/4).
- **Docs say it outright:** "If your app needs **webhooks, background jobs, or other server-side functionality**, then you'll still need to host your own backend for those use cases and call it from the extension." — https://shopify.dev/docs/api/app-home-ui-extension/latest.

### H. Label printing and PDF inside a Shopify-hosted extension — **the decisive risk**

- **Inside the extension sandbox:** rendering happens via remote-dom with a **subset of browser APIs**; extension code never touches the host DOM (https://shopify.dev/docs/apps/build/app-home; https://shopify.engineering/remote-rendering-ui-extensibility). There is **no documented print, file-download, blob, or iframe API** on the App Home target APIs (reference + Standard API fetched in full). `window.print()` availability/behavior from the sandbox: **UNVERIFIED** — but it cannot solve mm-exact pages anyway: printing a label sheet requires a *document* whose `@page { size: 25mm 25mm }` and zero margins control the output — that means a real HTML/PDF document, not admin UI components. **Spike 1 settles this empirically; expectation: NOT POSSIBLE.**
- **The official print surface needs our server:** Admin **print-action extensions** exist — targets `admin.product-details.print-action.render`, `admin.product-index.selection-print-action.render`, `admin.order-details.print-action.render`, `admin.order-index.selection-print-action.render` (https://shopify.dev/docs/api/admin-extensions/latest/target-apis/core-apis/standard-api, target list) — and the model is: the extension renders a small selection dialog, and the **`s-admin-print-action` component "specifies a URL for print operations … enabling custom print views optimized for physical or PDF printing"** (https://shopify.dev/docs/api/admin-extensions/latest/web-components/settings-and-templates/admin-print-action). The official tutorial: "**Serve a printable document from your app's backend.**" — https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-print-action. I.e., the printable page is exactly our existing `/print/:jobId` signed-token route. **No App Home print target exists**, and there is no documented custom-page-size print API for Dymo/Zebra 25×25 mm beyond serving your own document (which requires a host). A "Print" API listed in the local AI Toolkit's App Home skill could not be found in the bundled App Bridge types (0.7.0 `ShopifyGlobal` has no print) — treat as UNVERIFIED/likely iframe-model-only; POS has a hardware Printing API but it is POS-only (https://shopify.dev/changelog/release-notes/2026-07).
- **PDF generation in-extension:** `pdf-lib` (~400 KB min+gz) and `bwip-js` cannot fit the 64 KB compressed bundle, and the exception process denies "heavy libraries" (§2.A). **NOT POSSIBLE in a pure extension.**
- **Smallest no-server-ours alternative:** none. The printable document must be served from *some* HTTPS origin with per-job authorization; that origin is either ours (Railway) or a serverless function we still own and operate (Option 2 — still a server). Plainly: **there is no Shopify-hosted way to print Barcode Studio's labels.**

### I. Distribution, review and compliance

- **Distribution:** "Apps that use this model can ship only with **custom distribution**. If you want to build a public app you can distribute through the Shopify App Store, then use the iframe-based App Home solution." — https://shopify.dev/docs/api/app-home-ui-extension/latest and https://shopify.dev/docs/apps/build/app-home. **Direct conflict with the App Store plan** in `docs/shopify_app_deploy.md`.
- **Compliance webhooks:** mandatory topics are required "for all apps distributed in the Shopify App Store" (https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration) / "apps listed on the Shopify App Store" (https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance; https://shopify.dev/docs/api/webhooks/latest). A custom-distribution, no-customer-data app is not compelled by those pages — but our own audit already flags `shop/redact` erasure as a P0 before any real store (`docs/shopify_app_deploy.md` §1.3).
- **Webhooks without our server:** the TOML `uri` may be HTTPS, a relative path, **`pubsub://{project-id}:{topic-id}` or an EventBridge ARN** (app-configuration page). Delivery without our HTTPS endpoint is therefore *configurable* — but someone still has to own and run the Pub/Sub/EventBridge consumer, which is a server in different clothes. **Uninstall:** app-owned definitions are auto-deleted, values "temporarily retained" (§2.D) — better than our current stubs in one narrow sense, but metaobject cleanup and the retention window are UNVERIFIED.

### J. Security and operations without a server

- **Secrets:** an extension-only app has nothing to sign or exchange — no server code, no token in our hands (§2.C). The client secret still exists in the Dev Dashboard but has no app-side use; `printToken.server.ts`'s HMAC signing has no equivalent (and no need) in the extension model.
- **Kill switch:** env vars disappear; the equivalent is a flag read before every mutation — e.g., an app-owned metafield on `AppInstallation` ("writes disabled") checked by the extension before `productVariantsBulkUpdate`. That is a real-time, no-redeploy switch — but it is merchant-visible data, adds a read to every write path, and anyone with the flag's write path can flip it back. Redesign, not parity.
- **Logging/monitoring:** no server logs; no Shopify-provided telemetry service documented for extensions (UNVERIFIED whether external error reporting like Sentry is reachable — CSP/`appOrigins`, Spike 1). Debugging production issues falls back to merchant-side reproduction.
- **Updates:** `shopify app deploy` → new app version; for custom distribution the store picks the version up per the Dev Dashboard flow (mechanics UNVERIFIED — check "Deploy app versions" docs). Rollback = redeploy a previous version.

**Recommendation: Option 4 — stay on Railway.** The specific requirement that makes Shopify-only unrealistic is **printing millimetre-exact label documents** (and its sibling, PDF output): Shopify's only admin print mechanism serves the printable document from the app's own backend URL, so "no server" and "print labels" cannot both be true. The 64 KB bundle, absent webhooks/jobs, and custom-distribution-only rule each independently deepen the NO.

**Within Option 4, do these (each is small and independently valuable):**
1. **Verify and probably drop the static-IP add-on** (custom apps are exempt from the new IP allowlist rule; re-add only for a public launch). *(~0.5 pd)*
2. **Fix the compliance P0s** already identified in `docs/shopify_app_deploy.md` §1.3 (`shop/redact` real erasure, `app/uninstalled` full cleanup) — required for the client store regardless of any migration. *(~2–3 pd)*
3. **Unify webhook/Admin API versions** (toml `2027-01` vs client `2026-07`) — known audit item A3. *(~0.5 pd)*
4. **Optional modernization:** enable **`embedded_app_direct_api_access`** in the app TOML so the *current iframe app* can call the Admin API directly from the browser for latency-insensitive reads (config verified at https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration) — after Spike 3 timing data. *(~2–4 pd, optional)*
5. Run Spikes 1–3 anyway (≈2 days total) so the "Shopify-only" question is settled by *our own measurements*, not only by docs, before it ever resurfaces.

## 6. Migration and decommission runbook (Phase 6)

**NOT RECOMMENDED — no runbook is provided for a Shopify-only migration, because the verdict is NO-GO (§0, §4).** The alternative plan, in order (Windows PowerShell, all dashboard clicks noted; none of this touches the production client app's data):

1. **What:** Back up before anything. **Why:** everything below is safe, but the backup is the rollback. **How:** `npx prisma migrate status` (read-only) against staging; Railway → Postgres → Backup now. **Expected:** all 5 migrations applied; backup URL issued. **If it fails:** stop; fix migrations first.
2. **What:** Confirm what the static-IP add-on is for in the Railway billing page ("verify on screen"). **Why:** the IP allowlist rule excludes custom apps (https://shopify.dev/changelog/posts/ip-allowlists-are-now-required-for-public-apps) — the spend is likely dead weight today. **How:** Railway → Settings → Networking/Static IPs; check whether any Shopify config references it (it does not — allowlists are configured in the Dev Dashboard, which we have not set). **Expected:** either nothing depends on it (remove it; watch one week of webhook/API logs) or a documented dependency. **If it fails:** re-add the IP — it's a dashboard toggle.
3. **What:** Fix compliance webhooks (P0 from `docs/shopify_app_deploy.md` §1.3). **Why:** `shop/redact` currently deletes nothing; required before the client store and any public listing. **How:** implement full shop-scoped deletion in `webhooks.shop.redact.tsx` + `app.uninstalled` (delete all rows for the shop; code change, on a branch, through the normal PR/test/release checklist in `docs/PROJECT_OVERVIEW.md` §17). **Expected:** staging test: uninstall the dev-store install, verify rows gone. **If it fails:** restore the DB backup from step 1; the old behavior is unchanged by a failed deploy.
4. **What:** Unify API versions (A3): set toml `api_version` and `ApiVersion` to the same current stable. **Expected:** webhooks and Admin client on one version. **If it fails:** revert the toml deploy; versions are forward-only config.
5. **What:** (Optional, after Spike 3) enable `embedded_app_direct_api_access = true` in the app toml and move latency-insensitive reads to Direct API access in the iframe app. **Why:** cuts server round trips without any migration. **How:** edit `shopify.app.toml`, `shopify app deploy`, release the version. **Expected:** page loads skip the server for catalog reads. **If it fails:** set the flag false and redeploy; the server path still exists.
6. **Rollback at every stage:** Railway → Deployments → Redeploy previous; Shopify config → redeploy previous app version; kill switch unchanged (`ALLOW_SHOPIFY_WRITES=false` + restart).
7. **Revisit trigger:** if Shopify ships an App Home print/file API or a compute surface for extensions (watch the changelog), re-run Spikes 1 and 3 before reopening this plan.

## 7. Risks, costs, timeline, open questions (Phase 7)

**Top risks of the Shopify-only path (ranked), i.e., why NO-GO is robust:**
1. **Printing/PDF has no extension-side path** — print actions serve documents from the app's backend (§2.H). Structural, not incremental.
2. **64 KB bundle vs our rendering/PDF stack** — exception process denies "heavy libraries" (§2.A/H).
3. **No webhooks/background jobs** — Shopify's own reference says keep a backend for these (§2.G).
4. **Uniqueness/taken-set at 5,700–50,000 variants becomes per-click live scans** with rate-limit contention (§2.F).
5. **Custom-distribution-only** — kills the App Store plan in `docs/shopify_app_deploy.md` (§2.I).
6. One-way migration door ("the reverse isn't supported") — a wrong move is a rebuild (§2.B).

**Costs after the change vs today:** Shopify-only would save Railway plan + Postgres + static IPs (roughly the whole infra bill) but add nothing back for printing (impossible) — while Option 4 today can already shed the **static-IP** line (custom apps exempt from the IP-allowlist rule) and keep everything else. Maintenance: Option 1 trades one well-understood stack (React Router + Prisma) for a Preact/remote-DOM rewrite with weaker observability (no server logs).

**Timeline:** Spikes 1–7 ≈ **3–4 days total**. A full Shopify-only rewrite (if ever attempted with accepted NOT POSSIBLE rows) ≈ **8–16 weeks (≈60–100 person-days)**; the recommended Option 4 improvement set ≈ **5–10 person-days**.

**Questions for my seniors (max 8):**
1. Do we accept that **Shopify-only and the App Store plan are mutually exclusive** (custom-distribution-only), or is the public listing still the strategic goal? (This decides §4 by itself.)
2. Is label printing (Dymo/Zebra 25×25 mm exact) a hard requirement for every deployment, or could a "Shopify-lite" no-print variant of the app ever be worth shipping to a store without our server?
3. Can we **drop the Railway static-IP add-on now** (custom apps are exempt from the IP allowlist) and re-add it only for a public launch? (Needs one billing-page check.)
4. Who owns the **compliance-webhook P0 fix** (`shop/redact` erasure) and when — required before the client store regardless of hosting?
5. Are we OK to spend **2–3 days** running Spikes 1–3 so the decision rests on our own print/scan/CAS measurements rather than docs alone?
6. Should latency-insensitive reads move to **Direct API access inside the current iframe app** (`embedded_app_direct_api_access`, Spike 3 first) as the cheap modernization?
7. Does anyone need **multi-app concurrency** (several staff generating simultaneously) beyond the current one-job-per-shop lock? (Drives how much the CAS-counter redesign would matter in any future option.)
8. Timeline check: is the **Nov 20, 2026 IP-allowlist deadline** (public apps) relevant to any *other* app we run, so the exemption logic here isn't misapplied elsewhere?
